feat: host PHP websites and one-click WordPress, with MariaDB and a database browser

Adds PHP as a first-class runtime and WordPress as a create-site preset, so the
panel is no longer Node/.NET/static only.

PHP sites run as a supervised pool of php-cgi FastCGI workers (one php-cgi
serves one request at a time on Windows, so several run side by side and Caddy
load-balances across them). Caddy drives them with its built-in FastCGI
transport — no extra plugin. PHP, the VC++ runtime, MariaDB, Composer and the
Adminer database browser are downloadable components with pinned, hash-verified
releases; dependencies (PHP needs the VC++ runtime) install automatically.

WordPress is a preset on the Add-a-website page: the panel downloads a pinned
WordPress, provisions a per-site MariaDB database with a scoped login, writes
wp-config.php outside the web root, and starts the site — streaming the whole
thing to a terminal view. PHP repositories are detected automatically
(composer.json runs a Composer install on each deploy; a public/ folder becomes
the web root; a WordPress-shaped repo is recognised and pointed at the preset).

Each site gets a Databases tab: create, remove and reset passwords (own or
generated), within a per-site limit an admin can raise. The database browser
opens from there, signed in through the panel — it runs on a private,
loopback-only PHP server and is never exposed on a public domain.

The create-site wizard and the App page only offer what the server actually has
installed: PHP/WordPress/Node/Git kinds and the pnpm/yarn/bun package managers
are disabled with an explanation until the matching program is present, with
the wording differing for the owner (who can install it) and everyone else.

Also in this change: previews strip the headers that broke them over plain
HTTP (a framework's upgrade-insecure-requests no longer turns a preview's
assets into failing HTTPS requests), and the PHP health check uses a TCP probe
per worker rather than an HTTP request a FastCGI process cannot answer.
